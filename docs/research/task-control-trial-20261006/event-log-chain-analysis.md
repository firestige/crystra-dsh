## 结论与首轮修正

Session log **已经包含 Host 生成的 task-context 快照**：Plan digest、confirmed、stage、当前 Run 及最近成功回执。它们位于 plugin 来源的上下文消息中，不是 Agent 自述。因此不能说 Plan 状态和成功请求只能通过现场状态文件恢复。

本次可以仅凭日志建立“提案写入—状态采样—用户输入—后续状态”的链条。仍需源码解释的是：确认为什么没有被触发、某条拒绝对应哪个请求，以及被覆盖或因计划切换而留存的请求如何处置。缺口主要是决定与因果关联，不是再复制一套完整快照。

## 证据边界

- **日志事实**：记录了什么提案、工具结果、Host 快照和真实用户输入。工具写入成功不等于领域操作被接受。
- **代码解释**：将日志顺序与当时安装代码结合，解释门槛、消费时机和状态匹配；不能冒充已记录的决定事件。
- **现场佐证**：当前 task-confirmations、control-receipts、plan-runs、task-history 可佐证，但可替换文件不是历史事件账本。
- **Agent 叙述**：仅证明模型说过这些话，不用于证明系统发生过相应动作。

### 需要源码才能解释的部分

[task-chat-control.js](../../src/host/task-chat-control.js) 的确认条件要求顶层 `questions.length===0`，并且 grilling 没有 pending/disputed 条目。v2 顶层问题非空已经足以阻断原生确认提问；未满足条件时没有对应阻塞事件或明确反馈。

正式确认来自 Host 发出的提问，用户选择“确认此版本”后才调用 `flow.confirm`，绑定当前 digest 和 answerId。普通聊天里的“确认 v2”没有直接进入这个提交路径。因此本例不应解释为“已受理的确认正在异步落盘”。这一原因由日志输入和已安装代码共同确定；日志没有直接记录一次带规则原因的确认未触发决定。

两个顶层问题是“是否接受去掉 A-00、把探测并入 W-01”及“是否接受新计划使当前 plan-run 失效并重新确认”。这也暴露协议语义问题：模型把等待用户同意的事项写进了阻止确认的字段。是否把这种组合定义为非法提案，仍需先明确 requestConfirmation 的契约，不能仅凭本例决定。

[native-task-control.js](../../src/host/native-task-control.js) 写工具只原子替换目标文件；管控消费发生在 `agent/turn-stopping`。[task-control-request.js](../../src/host/task-control-request.js) 消费当时文件内容，没有保存每次写入的请求队列。结合上述顺序，可以解释为：03 没有在 04 替换它之前被消费，04 评估时缺少进入检查，因而拒绝。

但“305 拒绝的就是 04”及“03 因覆盖而未消费”不是日志中的显式关联事件，而是代码与顺序支持的解释。失败路径仅返回错误文本；它没有像成功路径一样保存请求 ID、digest 和时间回执。当前成功回执文件仍只有 M-00 两条，与日志快照一致。

# Crystra：项目方向与已定决策

更新于 2026-10-20。本文件承接项目讨论中已经确认的方向；当前实现与验证范围见 [当前状态](current-state.md)。它不是功能排期，也不替代运行中的受管共识审批。

## 为什么做

用户希望提供目标与文档，由 agent 研究、拆解和实现，自己承担产品经理、首席架构师和验收者的角色，并在反馈中持续迭代。

早期长程、多 agent 开发实践暴露出约定遗漏、重复建设、前后不一致、状态推进错误，以及上下文和高价 token 成本持续增长的问题。这些经历是项目动机，不是对所有模型或所有任务的统计结论。强模型完成长任务的案例，也不能反过来证明持续工作中的行为一致性已经得到保证。

Crystra 聚焦两个目标：

1. **一致性**：哪些自由留给强模型，哪些责任由确定机制承担；以合理成本减少明确的失约行为。
2. **成本**：把适合的执行交给更便宜的模型或已验证的代码，减少每次都重新推理和处理历史的成本。低价 token 替换高价 token 时，总 token 数可能增加，最终看总成本与效果。

我们接受不确定性无法消除，但可以控制一部分违约。Crystra 保障过程中的身份、效力和操作规则，忠实可靠地执行用户与 agent 提交的合法操作；它不成为内容正确性的最终裁判。

## 希望最终形成的使用体验

用户围绕一项持续工作给出目标、约定和反馈。agent 保留研究、规划、拆分步骤与选择局部方法的能力；系统可靠保留当前有效共识、责任、执行事实和修订依据，减少每次恢复都依赖长聊天上下文的负担。

重复工作中的局部能力逐渐被发现、验证和复用；环境或模式变化时退回探索，经重新验证后再复用。用户不必先识别热点或手写完整 workflow。需要人判断的内容和审批通过宿主的正常交互完成。

未来工作台让用户看清当前状态、待处理事项、工作历史和收益，并按任务选择适合的可视化。聊天保留过程记录，但不必承担所有状态展示与交互。这是目标体验，不表示工作台已经实现或已排期。

## 已确定的方案与选择理由

### 1. 依托 DSH，做执行过程增强

早期为实现目标而自行建设 harness 的路线已经调整。当前采用 DSH 插件：DSH 拥有 agent loop、模型、工具执行、会话和调度；Crystra 提供共识、承诺核验、独立反思与结晶能力。

理由是强模型和宿主已经能够规划、执行并组织协作。把每次探索预先锁死在固定流程、多 role 或 Commander 中，会限制模型能力，并重新引入中央上下文和编排负担。是否使用多 agent、如何拆分任务交给 DSH 和 agent；Crystra 不因成本目标而内置另一套调度器。

分工有成本价值：输入准备、工具调用、结果整理、正常时静默等边界清楚、无需持续 ReAct 探索的工作，可以使用较便宜的模型；关键研究和核心代码工作使用合适的强模型。这是分配原则，不是“所有一次性任务都简单”，也不是当前已有自动最优模型路由器。

对能收敛为明确选项的判断，倾向让模型接收有界上下文、作分类或提出候选；状态推进、效力与回执由代码管理。这一原则不表示所有研究都能压成一次调用，也不要求 Crystra 自建调度。

### 2. 共识与运行状态由代码可靠管理

共识是明确范围内有身份、版本与效力的约定，不等同于“检索到一段相关记忆”。代码和设计文档可以承载共识内容，但检索命中、文件存在或模型声称读过，不等于正式装载了正确版本。

我们选择 **Squidex 作为共识内容管理底座**，采用其版本、草稿、发布、历史和权限能力，通过胶水层接入，不维护特殊分叉。PostgreSQL 由共识服务使用，不让后台业务直接耦合 SQL。普通知识库与有约束效力的共识在语义和管理上隔离；知识检索结果不得直接升级为生效约定。当前未把通用知识库作为已交付组件。

选择理由：Git 提供版本与历史，但单独不能完成效力、发布权限和受管操作；普通 memory 的自动提取、覆盖或相关性检索也不能代替可靠的共识管理。Squidex 更接近所需内容生命周期，但仍由 Crystra 补齐精确引用、候选授权、操作回执、装载与切换边界。

DSH JSONL/session 提供持久化和会话恢复底座；Crystra 的领域代码维护承诺与责任规则。agent 可以从持久事实重建当前状态，不靠角色自报来维护状态机。没有另引入状态机框架或远端状态服务的已定要求。

共识加载不能靠模型随意挑选：绑定精确发布身份和范围，核验效力与依赖，保留装载历史；旧版本不能被静默覆盖，新版本也不能被未批准地启用。内容正确性由用户和 agent 判断，系统负责合法操作及结果可靠保存。

### 3. Barrier 检查明确的履约，不替代设计判断

agent 在步骤前提出可检查的承诺，系统把支持的承诺编译为确定性检查，并根据实际工具执行事实核验。Barrier 的公开结果是 GO/NO_GO，不负责写审查意见或指定修复方案。

例如：“运行某测试并检查退出码”不需要事先知道测试会通过。执行后若没有运行，却声称测试已经证明某结论，执行承诺不能闭合。若实际运行失败，则执行事实与结果验收应分别看声明的断言，不把未知答案预设成事实。

允许有依据地修订承诺，但不得靠删除责任、复用别的执行或修改状态来过关。当前支持的有限修订与未来可能的修订形式须区分，见状态文档。

选择理由：一些低级幻觉可以被外置事实检查发现，不必让另一模型判断一切。它不能证明 agent 理解了某文件、设计充分或结论可泛化，也不能保证所有行为都被声明。不同失效应分层处理，不把所有问题都塞给 Barrier。

### 4. 反思独立研究核心代码质量

反思由宿主选定的高阶模型在独立会话读取相关源码、运行给定回归或实验，针对正确性、鲁棒性和性能提出具体观察及建议。未实测的内容保留为推测或待验证问题。

选择理由：这类工作需要具体推理、实验和方案设计，不能缩成一个无理由的 gate。反思与 Barrier 分开；报告不能批准共识、释放责任或认证代码正确。工作 agent 与用户决定如何吸收建议。

策略、prompt、模型和实验集随实践调整；Crystra 提供机制，不把某套永久最佳反思策略写死。

### 5. 结晶是有验证与回退的局部复用

结晶的长期方向类似 JIT：观察持续工作中的重复边界，主动推动评估；agent 可接受、拒绝或推迟，并选择具体实现。结晶产物可以是代码或其他局部能力，不限定为固定 workflow，也不要求把大任务整体固化。

候选先明确适用范围、绑定实际材料，再对拍独立原路径结果；验证通过后才接管适用调用。输入、模式、共识或执行环境发生相关变化时，拒绝不再适用的版本或退回原路径，重新探索、验证与准入。快路径结果不能充当自己的独立原路径验证依据。

选择理由：首次冷任务不一定有复用价值，首次就替换也缺少独立校准。持续观察与对拍可降低过早固化的风险。历史对拍仍不能证明未来任意输入都正确；不能安全自动处理的不确定情况应保留信息并交给 agent 或用户判断，而不是静默声称可靠。

成本应包含评估、构建、对拍和回退开销。保守收益策略可以逐步调优；热点发现、净收益预测和通用正确性不是同一个问题，不能用机制 happy path 推导所有任务都有收益。

### 6. 组件按职责分开，当前一个仓库交付

当前在同一仓库中按职责组织后台组件，以 DSH 插件交付。共识、Barrier、反思、结晶不强绑定成一个业务流程；复用机械基础设施，不合并各自策略。通过具体 Adapter 隔离 DSH 接口变化，按需修兼容，而不增加通用框架或维护 DSH 分叉。

DSH 尚在快速迭代，引用位置、函数名和事件格式变化优先在适配层处理。若上游取消必要机制，需要重新评估，不承诺适配层可以抵消任意上游变化。

MVP 采用单机、本地服务，优先复用 DSH 的安装、配置、审批、持久化和观测机制。薄 CLI 补足安装前环境检查、事务回退与诊断；直接 plugin add 时也防御缺少部件的情况。不自动安装容器环境，不以新增多租户、防篡改或隐私加密等企业能力扩大当前交付范围。

## 未来方向：保留意图，不生成待办

| 方向 | 已确认的目标或原则 | 尚未决定的部分 |
| --- | --- | --- |
| 工作台 | 独立控制台；退出不影响 DSH 服务；按用户已定技术偏好使用 React + Tailwind CSS，并复用已有有用组件；状态、任务可视化、历史和收益有独立视图 | 页面、任务视图、完整通信方案、开发顺序和交付范围 |
| JSONIR | 定义工作台需要的展示语义，是 payload 契约，不是传输协议；优先复用已有公共契约 | 字段、版本与具体任务语义；不能在工作台需求未明时提前冻结全套 schema |
| 事件与通信 | 优先使用 DSH 的内部事件、观测及插件生态；语义投影和传输适配分开考虑 | 具体前端连接实现与适配范围，是否需要额外组件 |
| 结晶与成本 | 发现应由系统推动，用户无需主动挑选场景；局部验证、适用性与回退长期成立 | 收益预测、阈值、更多边界与执行器、长期质量评价及整理策略 |
| 反思与协作 | 高阶模型集中处理有价值的核心问题；简单边界可交给低价模型 | 最佳模型组合、自动触发策略、实验生成与反馈策略 |
| 共识与知识库 | 可靠共识管理与普通知识吸收必须隔离；人应能方便阅读文档 | 知识库组件、接入方式、跨系统同步及更多装载策略 |

以上未决定项是探索边界，不是任务池、排期或要求 agent 自动补齐的缺口。新场景需要验证时先提出假设与判定条件，再决定是否做 spike。实验优先使用已知结果、可区分归因的场景；比较结晶机制收益时保留纯 agent 基准，并考虑冷启动、长尾及验证开销。

## 如何继续演进

采用原型与敏捷循环：明确本轮共识和目标 → 实现并验证 → 由观察与反馈形成新共识 → 再进入下一轮。不能把曾经讨论过的手段自动升级成需求。

发生方向冲突时回到目标与选择理由，不以“已有代码很多”维护旧方案，也不以“模型现在很强”推断所有外置责任都可取消。改变本文件记录的已定方向，须有用户确认的目标或方案更新；常规实现选择仍在已授权任务内自主推进。

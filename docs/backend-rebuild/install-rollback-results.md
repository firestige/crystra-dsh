# 原生插件安装失败回退、卸载与重装实验

2026-10-13。此项是验证安装流程的 spike，不是已交付的正式安装器。发布包与实际 Web profile 未改动。

## 环境与方法

使用真实 DSH 0.1.5-rc.2 CLI、pnpm 11.23.0、本机已有 OrbStack 的 Docker 29.4.0 兼容接口及 Compose。安装包是带 preinstall/postinstall 的最小本地插件夹具；全部 package add/install/remove 都由 `dsh plugin --profile probe` 转发，不重写依赖解析。Squidex 7.24.0 和 PostgreSQL/PostGIS 使用既有测试镜像，启动独立 Compose 项目与两个新卷，初始化真实 app/schema/草稿内容；没有调用用户日常共识库。

每次使用临时 DSH_HOME、独立 profile/缓存和独立容器项目。预先安装另一个插件，准备模型/UI/LAN 设置、凭据记录及数据保护标记。安装中途故障发生在服务启动、CMS app 建立及凭据部分写入之后。卸载后的重装故障使用已有的保留卷，验证不能因本次失败删除旧数据。

最终运行：artifacts/backend-rebuild/install-rollback/results.json。9 项全部通过。打包边界回归 2/2 通过；没有修改生产行为，未将之前后台 388 项当作本次新跑结果。

## 结果

| 场景 | 观察及断言 |
| --- | --- |
| 原生失败残余与补偿恢复 | 原生 add 非零退出后留下包和配置变化；受控恢复后精确回到原状态 |
| 容器环境检查失败 | 注入不可用的引擎候选，preinstall exit 23；服务未启动；配置逐字节和依赖目录文件/链接/权限均恢复 |
| 生命周期脚本未授权 | add 失败，钩子未执行；其可能留下的依赖/锁文件/包文件同样撤销 |
| 初始化中途失败 | 已启动服务、建立 CMS app、部分写入凭据后 exit 23；本次新建容器、网络和卷清除；原配置/依赖及文件数据保护标记保留 |
| 正常安装 | 原插件仍登记且内容完整，新插件登记；真实 CMS 含一条保护数据 |
| 正常卸载 | 原生 remove 删除新插件及登记，局部清理停服务；保留两个数据卷，保留安装后用户新增设置及原模型/UI/LAN/凭据 |
| 保留数据后的重装中途失败 | 仅撤销本次启动与配置变化，既有两个卷保留 |
| 再次安装 | 服务恢复，读取同一条内容，ID/正文/版本完全一致，没有重复创建 |
| 重复卸载 | 再次调用不破坏已有配置或保留卷 |

最后对日常实际 DSH 的 settings、真实 .credentials.yaml、Web profile package/lock/workspace/patch 和 LAN Caddyfile 做前后字节核对，保持不变。测试完成后仅显式清理本实验容器、网络和卷；卸载保留数据的断言在这次实验最终清场之前已完成。

## DSH/pnpm 不自动完成的部分

恢复旧 package.json、锁文件等后运行原生 `install --offline --ignore-scripts --frozen-lockfile`，仍可能留下失败安装中未登记的包目录。另行验证 `prune`、`install --force` 也未删除该残余。不能把返回 0 当作回退完成。

已验证的补偿方案：安装调用方在操作前保存 profile/config 精确内容及 node_modules 快照，并记录原有服务卷；失败后停止本次服务，只在原来没有数据卷时删除本次新卷，恢复配置，再让原生 pnpm 重建旧依赖图。核对目录仍不一致时，以操作前的目录快照恢复，随后再次核对文件内容、符号链接和权限。依赖解析和正常卸载仍交给原生工具，这层只保存和撤销本次操作。

正常卸载不能恢复整个安装前 settings 快照，否则会抹掉安装后用户修改。实验采用只去掉自有设置/凭据键、原生 remove 包和停止自有服务，明确保留数据卷。

## 探针修正与真实异常

- 首次失败回归发现原生 install 无法清掉未登记包，已保留失败结果，不把它写成成功。
- 实际引擎默认网络地址池耗尽，容器未能启动；这一轮的回退断言通过，但没有到预定 CMS 初始化断点，不能代替中途失败场景。随后枚举已有网络，选择无重叠的独立子网补测，没有删除用户网络或改引擎全局设置。
- 草稿内容默认列表不可见，数据保护探针初次错误期待一条已发布查询结果。按现有 Squidex 客户端的 X-Unpublished: 1 契约修正后重测，没有为了过测试发布共识或放宽数据断言。

## 可复现方式与边界

执行 `node scripts/backend/install-rollback-spike.mjs`。要求本机已有 DSH/pnpm 和可用的 Docker 兼容接口/Compose及测试镜像；脚本不安装容器环境。入口尝试 docker/podman，但本轮只验证了 OrbStack 的 Docker 接口，不能据此声称 Podman 或其它平台已验收。保护数据是隔离 CMS 草稿，文件设置/凭据是合成保护标记；正式 Crystra 的全部初始化 schema/workflow、真实密钥登记和发布审批未在本轮新增验证。

此方案尚需接入正式包与生命周期。当前快照在安装调用进程内管理，实验没有证明调用进程被 SIGKILL 后自动恢复，也未证明运行中 profile 被其他进程同时修改时可无损回退。正式接入必须约束安装期间的写入并保留可恢复记录，不能直接把整个旧快照覆盖到存在并发修改的 profile。正常卸载默认保留共识数据；清空数据是另一项显式操作。包缓存与已有镜像不作全局清理。
